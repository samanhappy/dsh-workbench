# AGENTS.md

## Project

dsh-workbench (`@samanhappy/dsh-workbench`) is a public, open-source DeepSeek Harness (DSH) static-bundle plugin. It adds a "workbench" sidebar entry whose panel manages local Git, GitLab MRs / GitHub PRs and their Issues via the local `glab` / `gh` CLIs, plus Aliyun DMS ticket approval and SLS log queries via the local `aliyun` CLI, a read-only PingCode work-item page driven by a local pingcode skill's Python scripts (`python3 <skill>/scripts/api_call.py`, see `src/host/pingcode.ts`), a GitHub notifications page driven by the local `gh` CLI (see `src/host/notifications.ts`), and a skills management page driven by the skills.sh `npx skills` CLI + the public skills.sh search endpoint (see `src/host/skills.ts`). The GitLab / GitHub, Aliyun, PingCode and skills.sh integrations are optional and only work when the corresponding local CLI is installed and logged in. No dynamic runner, no approval, no steering.

## Commands

Package manager: **npm**. Development needs Node.js >= 22.15.0 (`engines`); using the plugin does not.

```bash
npm install             # devDependencies
npm run build           # esbuild: src/host → index.js, src/client → lib/client.js
npm run typecheck:setup # install pinned public DSH contract packages (--no-save)
npm run typecheck       # tsc --noEmit
npm test                # node --test, auto-builds first
npm run smoke           # host-half smoke against REAL glab / gh / aliyun (needs them logged in)
npm run sim             # client-half behavior simulation (stubbed environment)
```

**Rule: run `npm run build` after any change under `src/`.** Both `index.js` (host half) and `lib/client.js` (client half) are committed build artifacts regenerated by `build.mjs` — never hand-edit them. CI rebuilds both and checks they are byte-for-byte reproducible; committing source without the regenerated artifacts fails that check.

## Implementation reuse

- **Reuse existing components and styles first.** Before adding UI, inspect comparable feature pages and the shared components, styles, icons, and runtime helpers. Use the same building blocks for the same UI role so new pages stay visually and behaviorally consistent.
- Add feature-specific components or CSS only when existing building blocks cannot meet the requirement. Keep those additions scoped to the actual difference; do not copy shared styles or override them with near-identical values.
- Check shared-style changes against their other callers, and compare new UI with an existing page before considering it complete.

## Open-source hygiene

- Tracked files must not contain real private hostnames, private IPs, company project names, colleague names, phone numbers, credentials or tokens. Tests and the smoke harness use neutral fixtures or read configuration from environment variables.
- Do not claim capabilities the code does not have. Public docs describe purpose, boundaries, contracts, setup and limitations; source and tests are the fine-grained source of truth.

## Docs convention

**Code is the single fine-grained source of truth.** `docs/` only carries what cannot be inferred from the source, or what breaks if someone gets it wrong: purpose and boundaries, module responsibilities, external contracts and invariants, flow semantics, extension points, known limitations, operational steps.

- **Never restate the implementation**: route/parameter lists, CLI argv, cache TTL values and defaults, data-structure field tables, per-button UI behaviour, DOM/CSS details, build-artifact internals. Source and tests are authoritative for those.
- The default action for a feature change is *code + tests*. Touch `docs/` only when a **capability boundary, external contract, invariant, or user-visible semantic** changes.
- Write *why it is designed this way*, not implementation steps or change history. Keep each doc scannable in one screen; avoid very long single lines.
- Before adding a doc line, ask: would a reader learn this by reading the code? If yes, don't write it.
